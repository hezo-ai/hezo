## Code quality principles

These are the bar for every change that lands in the codebase. Engineers respect them when writing; QA enforces them when reviewing. A change that violates any of them is not done.

- **DRY.** The second appearance of the same shape — a validation rule, a format, a request shape, a piece of UI — moves to one home and both places call it. Search the shared packages and existing helpers before writing new code.
- **High cohesion, low coupling.** One module owns one concern. Dependencies flow one direction. When a file mixes concerns or grows past roughly 300 lines, split it by concern.
- **Reuse the established pattern over an ad-hoc shape.** The codebase has already chosen its patterns for mutations, transactions, route authorization, shared enums and background work. Do not invent a parallel pattern when one fits, and do not mix paradigms within a single surface. Read the repo's AGENTS.md for the ones it names.
- **Build what was planned, once — never invent a fallback.** When a plan, spec or existing design names the mechanism, that mechanism is the *only* way it is done: no second path that engages when the first is unavailable, no capability check that quietly takes the other branch, no rollout flag that leaves the new mechanism off, no `catch` that retries the work a different way. **If the designated mechanism fails, fail loudly**, with a message naming what broke and what to check. When it genuinely cannot work in some environment, that is an architectural decision and not yours to make alone: state the constraint and the trade-off, ask the admin, and wait.
- **No redundant or dead code — strip what a change supersedes, in the same change.** When you replace an implementation, migrate callers, or rename a symbol, delete the superseded version now rather than leaving it beside the new one. Half-finished implementations, commented-out blocks, single-call wrappers that add no abstraction, unused exports, orphaned helpers and compat shims for code that no longer ships are all dead weight. Prove a symbol has no remaining callers with the compiler and grep before and after you cut it.
- **Maintainability over cleverness.** A clear ten-line sequence beats a clever one-liner. Flatten nested conditionals, prefer early returns, and name intermediate values. The next reader is often another agent waking on a future heartbeat and must pick up the file cold.
- **Performance is a correctness requirement, not an optimisation.** N+1 queries, unbounded loops, missing indexes on hot paths, client-blocking synchronous work and refetch storms are bugs. State what a change improved and how you observed it; "should be faster" is not a result.
- **Design for the real workload, and budget what each request costs.** Decide the reference workload up front — concurrent users or jobs, total rows, largest single record — and design against it rather than the demo. Concretely:
  - Bound every list endpoint in **row count and row width**. Never return a column whose size has no ceiling (a log, a document body, an attachment blob) from a list route, because the page size multiplies it.
  - Know how many queries, cache reads and network round trips one request costs, and treat that as a budget. Fold repeated lookups into one query, batch or join instead of looping, and cache what is hot and rarely changing.
  - Filter, limit and aggregate in the query, not in application code. On tables that only grow, prefer keyset pagination and a has-more flag over counting the whole table.
  - Index the hot path, and index what the query actually asks for: a function applied to a column defeats a plain column index, and filter-then-sort-then-limit wants a composite index in that order. Any query on a timer or a per-request path ships with its index in the same change.
  - Never write a row that has not changed — a no-op update still writes, still invalidates caches, and on many engines leaves a dead row behind.
  - Share resources rather than multiplying them per unit of work: one pooled, refcounted, idle-released resource keyed by what it is actually keyed on, not one per request or job.
  - Bound every recurring job with a limit on its scan, log a skipped tick, and match the interval to how fast the thing changes.
  - Give every cache an invalidation story and a bound — a TTL, a size cap, explicit invalidation, or a lifecycle that ends — in a comment next to the declaration.
  - Batch high-frequency events into periodic messages and handle a slow consumer explicitly; an ignored send result is unbounded server-side buffering.
- **Load progressively: cheap structure first, heavy content on demand.** A first paint returns the shape of the data — how many items, their order, a size hint each — so the layout settles with no shift. Fetch the expensive per-item payloads only for what the user reaches, batching what becomes visible together.
- **Stream; do not copy.** Data that can exceed a few megabytes is streamed end to end, never collected into an array, joined into one string, or buffered before being written or sent. This covers file transfer, import/export, backups, report generation, and any body without a hard size cap.
- **A new mutex, lock or queue is a throughput ceiling.** Say in a comment what it protects and why a narrower scope is insufficient, hold it for the shortest span, and never hold it across I/O.
- **Deleting the user's data is the operator's decision, never a default.** A table that only grows is a query-design problem, not a licence to prune. Records of what the system did, what it cost, and who changed what may be wanted forever. Where reclamation is genuinely needed it is an explicit control the operator triggers, and it says plainly what it will remove.
- **Testability is non-negotiable.** Code that cannot be tested without elaborate mocking is poorly designed — refactor the seams. Pure logic stays pure; side effects sit at boundaries. Prefer integration tests against the real stack over heavily-mocked unit tests.
- **Tests are typechecked code; lean on the compiler for refactors.** Test files must be inside the typecheck graph so a broken test signature fails the same as broken source. Before a sweeping change, confirm the suite is type-checked, then let the type errors enumerate every call site instead of discovering breakage at runtime. A refactor that only passes because the broken code was never type-checked is not done.
- **A green test run must have a quiet log.** The dividing line is intent. Output a test **deliberately produces or asserts on** is legitimate at any level, including an error line from exercising an error path. What is a defect is *incidental* output the test neither intends nor asserts on — a side-effect failure that logs but does not fail the assertion. Fix it at the source. Engineers keep the log quiet while writing; QA treats a noisy pass as a finding, after confirming the output is incidental.
- **Search before you write.** Before adding a helper, constant, hook, component or middleware, grep first. Reuse and extend what exists; if a near-fit needs a small generalisation, generalise it once in place rather than writing a parallel implementation.
- **Install before you build, with the project's package manager.** Honour whatever the lockfile and the repo's AGENTS.md name. Before any typecheck, build or test, install dependencies **once and wait for that install to finish** — a typecheck against an empty `node_modules` is meaningless and every error it prints is noise. Never launch installs concurrently or in the background: two installs in one directory contend on the lockfile and stall each other.
