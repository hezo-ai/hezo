## Code quality principles

These are the bar for every change that lands in the codebase. They are hard musts, not aspirations — Engineers respect them when writing, QA enforces them when reviewing and on heartbeat. Each principle is tied to a pattern that already exists in this codebase; reuse it before inventing a parallel shape.

- **DRY (Don't Repeat Yourself).** Two or three appearances of the same shape → extract a helper, constant, hook, middleware, or component. Search `packages/shared/`, per-package `lib/` directories, and existing hooks like `useOptimisticMutation` before writing new code. Precedents that codified this: `withTransaction` consolidating 16 hand-rolled transaction blocks, `requireTeamAccess` Hono middleware replacing 27 hand-rolled auth guards, the `buildJudgeScript` factory that lets Codex and Gemini stop-hook scripts declare only their differences.
- **High cohesion, low coupling.** One module owns one concern. Server services do not import web code; route handlers do not reach into another route's internals; dependencies flow one direction (UI → query hooks → API → service → DB). When a file mixes concerns or grows past the comfort zone (≈300 lines), split it by concern. Precedents: `comment-renderers.tsx` split into per-content-type files with a typed registry dispatcher; `settings/general.tsx` split into per-section components with hoisted shared queries.
- **Reuse established patterns over ad-hoc shapes.** The codebase has already chosen its patterns: `useOptimisticMutation` for field edits, response-driven mutations for security-sensitive flows (`useFulfillCredential` and friends), invalidate-and-refetch for long-running validation flows, `withTransaction` for multi-write sequences, `requireTeamAccess` middleware for route authorization, `@hezo/shared` enums for status / type strings, slugs in URLs vs UUIDs internally, `trackBackground` for fire-and-forget work. Do not invent a parallel pattern when an existing one fits; do not mix paradigms within a single surface.
- **Build what was planned, once — never invent a fallback.** When a plan, spec, or existing design names the mechanism for something, that mechanism is the *only* way it is done. Do not add a second path that engages when the first one is unavailable, unproven, or inconvenient: no `?? legacyBehaviour()`, no capability check that quietly takes the other branch, no rollout flag that leaves the new mechanism off by default, no `catch` that retries the work a different way. Each of those looks careful on its own; together they give the system two shapes, and the shape nobody exercises locally is the one production runs. Worse, a fallback hides the failure it was added for — the operator sees a healthy-looking system doing the wrong thing instead of an error naming what broke. **If the designated mechanism fails, fail loudly**, with a message that says what broke and what to check. When it genuinely cannot work in some environment, that is an architectural decision and not yours to make alone: state the constraint and the trade-off, ask the admin, and wait for an answer — which is often "then it is unsupported there" rather than "then add a second path". A deliberate exception is fine once the admin has chosen it, and it is written down as an exception.
- **No redundant or dead code — strip what a change supersedes, in the same change.** Removing the old is part of adding the new: when you replace an implementation, migrate callers to a new helper, rename or move a symbol, or change an approach, delete the superseded version in the *same* change — never leave the old code sitting beside the new "until later" or commented out as a reference. Half-finished implementations, commented-out blocks, single-call wrappers that add no abstraction, unused exports, helpers orphaned once their last caller moved, now-unreachable branches, "in case we need it later" abstractions, and backwards-compat shims for code that no longer ships are all dead weight — delete, do not commit. Lean on the compiler and `grep` to prove a symbol has no remaining callers before and after you cut it. Engineers remove the old code as they write the new; QA treats any leftover old, redundant, or dead code as a finding and rejects the change until it is gone.
- **Maintainability over cleverness.** A clear ten-line sequence beats a clever one-liner. Keep cyclomatic complexity low: flatten nested conditionals, prefer early returns, name intermediate values so the reader does not have to hold a chain in their head. The next reader of this code is often another agent waking on a future heartbeat — they must be able to pick up the file cold.
- **Performance is a correctness requirement, not an optimisation.** N+1 queries, unbounded loops, missing indexes on hot paths, inadvertent client-blocking synchronous work, and unnecessary refetch storms are bugs, not nice-to-haves. When in doubt, measure — and state what a change improved and how you observed it. "Should be faster" is not a result.
- **Design for the load and the data volume the system will actually see, not the demo.** Decide the reference workload up front (concurrent users or jobs, total rows, largest single record) and design against it. Concretely: every list endpoint is bounded in **row count and row width** — never return a column whose size has no ceiling (a log, a document body, an attachment blob) from a list route, because the page size multiplies it; never do per-row work in a serial loop when it can be batched or joined; and never put work whose cost grows with accumulated data inside a fixed-cadence timer, because it silently gets slower forever.
- **Budget the resource calls each request makes, and cut them.** Know how many database queries, cache reads, and network round trips one request costs, and treat that number as a budget rather than an accident. Fold repeated lookups into one query, batch or join instead of looping, and resolve a set of ids in a single call. Cache what is hot and rarely changing — in-process for single-instance state, an external cache for shared state — instead of re-deriving or re-fetching it per request. A request whose cost grows with the number of rows it renders is a defect, however fast it feels on a small dataset.
- **Load progressively: cheap structure first, heavy content on demand.** A first paint should return the *shape* of the data — how many items, their order, and a size hint per item — so the user immediately sees how much there is and the layout settles with no shift or jumping scrollbar. Fetch the expensive per-item payloads (bodies, previews, attachments, signed URLs) only for what the user actually reaches, batching the requests for what becomes visible together. This is strictly better than both alternatives: loading everything up front is slow and mostly wasted, while paginating away the structure hides the total from the user and breaks scroll position.
- **Share resources; do not multiply them per unit of work.** Prefer one pooled, refcounted, idle-released resource over one per request, job, or tenant — connection pools, HTTP clients, compiled templates, caches, derived keys. Ask what the resource's natural key is and key it by that. Deriving or constructing something expensive per call, when it is identical every time, is one of the most common and most invisible sources of load.
- **A new mutex, lock, or queue is a throughput ceiling.** Say in a comment what it protects and why a narrower scope would not be enough, hold it for the shortest possible span, and never hold it across I/O you could do outside it. Two independent pieces of work serialized by a shared lock will look fine in testing and fall over under concurrency.
- **Stream; do not copy.** Data that can exceed a few megabytes is streamed end to end — never collected into an array, joined into one string, or buffered into memory before being written, sent, or transformed. This applies to file transfer, import/export, backups, report generation, and any request or response body without a hard size cap. Buffering "just for now" is how a feature that worked on test data kills the process on real data.
- **Index the hot path, and index what the query actually asks for.** An index a predicate cannot use is not an index: a function applied to the column (lower-casing, casting, extracting from JSON) defeats a plain column index. For filter-then-sort-then-limit queries the index is composite, in that order. Any query on a timer or on a per-request path ships with its supporting index in the *same* change.
- **Filter, limit, and aggregate in the query, not in application code.** Loading a large record to keep its last few lines, fetching a collection to count it, or reading every row to find one, are query bugs. On tables that only grow, prefer keyset pagination and a has-more flag over counting the whole table to render a page number.
- **Never write a row that has not changed.** A no-op update still writes, still invalidates caches, still replicates, and on many engines still leaves a dead row behind. Guard writes with a real change check. This matters most exactly where it is least visible: a status-sync loop that rewrites unchanged rows on every tick.
- **Every recurring job is bounded, observable, and paced to what it watches.** Put a limit on every scan so a backlog cannot produce an unbounded batch; log when a run is skipped because the previous one is still going, since a silently-dropped tick means stale state with no signal; and match the interval to how fast the thing actually changes rather than to the fastest thing it might.
- **A cache needs an invalidation story and a bound.** State the eviction rule when you add it — a TTL, a size cap, explicit invalidation, or a lifecycle that ends — and write it in a comment next to the declaration. A long-lived map with none of those is a memory leak with good intentions. Caches holding sensitive data must also say when they are cleared.
- **Coalesce on the wire and respect backpressure.** Batch high-frequency events into periodic messages instead of sending one per item, and handle a slow consumer explicitly. An ignored "did this send succeed" result is unbounded server-side buffering waiting to happen.
- **Deleting the user's data is the operator's decision, never a default.** A table that only grows is a performance problem to solve with query design — pagination, bounded projections, indexes — not a licence to prune. Records of what the system did, what it cost, and who changed what are things a user may deliberately want to keep forever; deleting them to save yourself a query plan is destroying data to avoid doing the work. Where reclamation is genuinely needed, it is an explicit control the operator triggers, it says plainly what it will remove, and it must not stall the system while it runs. Only internal bookkeeping with no user-facing surface may be swept automatically — and say in a comment why it qualifies.
- **Testability is non-negotiable.** Code that cannot be tested without elaborate mocking is poorly designed — refactor the seams. Pure logic stays pure; side effects sit at boundaries. Prefer integration tests against the real Hono + PGlite stack (or `renderApp()` in the web tier) over heavily-mocked unit tests, per AGENTS.md.
- **Tests are typechecked code; lean on the compiler for refactors.** Test files must be inside the package's `tsc --noEmit` graph (each package's `tsconfig.json` `include` covers its `test/` directory), so `bun run typecheck` catches a broken test signature the same as broken source. Before a sweeping change — renaming a route param, changing a hook's arguments, reshaping a shared type — confirm the suite is type-checked, then let the type errors enumerate every call site (tests included) instead of discovering breakage at runtime. If you find a `test/` tree excluded from typecheck, fix the `tsconfig` first (mirror the web package: add `test` to `include`, map the package's own `@<scope>/<pkg>/*` path, and add ambient declarations for any transitively-imported binary assets) — then refactor with the compiler as your safety net. A refactor that only "passes" because the broken code was never type-checked is not done.
- **A green test run must have a quiet log by default.** A passing test should print nothing unless it *means* to — the dividing line is intent, not log level. Output a test **deliberately produces or asserts on** is expected and entirely legitimate at any level: an `[error]`/`[warn]` line from exercising an error path, a warn branch, or a rejected request, *and equally* any non-failure/diagnostic output a test explicitly wants surfaced. What is a defect is *incidental* output the test neither intends nor asserts on — a side-effect failure that prints to the log but does **not** fail the assertion (fix it at the source, don't tolerate it as background noise), and gratuitous verbosity beyond what the test means to show. The incidental patterns that bite (catalogued in AGENTS.md → *No spurious `[error]`/`[warn]` in unit-test output*): orphaned fire-and-forget work (`xxx(...).catch((e) => log.error(...))`) races test teardown and logs `PGlite is closing/closed` — wrap it in `trackBackground(...)` (`packages/server/src/lib/background.ts`) so `safeClose` drains it before the DB closes; an inline docker mock missing a method that production calls as a side-effect throws `docker.containerLogs is not a function` — build from `createStubDocker({ ... })`, never a hand-rolled partial; and a `Route error on …` line from `app.onError` on an expected-failure test means the route returned a 500 where a 4xx was honest — catch the known constraint locally (`isFkViolation`) and return `err(c, ...)`. Engineers keep the log quiet while writing; QA treats a noisy pass as a finding, not a cosmetic nit — the suite is green, so the noise is easy to wave through — but first confirm the output is incidental, not something the test deliberately exercises or wants surfaced.
- **Search before you write.** Before adding a new helper, constant, hook, component, or middleware, grep first. Reuse and extend existing utilities; do not duplicate. If a near-fit needs a small generalisation, generalise it once in place — do not write a parallel implementation alongside.
- **Install before you build, with the project's package manager.** Use `bun`/`bunx` for Node.js projects — never `npx`, which silently fetches an unrelated registry package when the binary is not a local dependency (the tool you get is not the tool you wanted). If the project's `AGENTS.md` or lockfile names a different package manager, honour that one. Before any typecheck, build, or test, install dependencies **once and wait for that install to finish** — a typecheck against an empty `node_modules` is meaningless and every error it prints is noise. Never launch installs concurrently or in the background: two installs in one directory contend on the lockfile and cache and stall each other, leaving `node_modules` empty. One foreground install, awaited, then build.

A change that violates any of these is not done. Engineers self-enforce before requesting review; QA rejects changes that fall short and files cleanup tasks for existing code that already does.
